1. PROJECT OVERVIEW
================================================================================

SalesTrack is a mobile-first Progressive Web App (PWA) for sales force management.
It has 4 user roles: Admin, Owner, Salesman, Accountant.

Core features:
- Admin creates Owner accounts
- Owner creates Salesman and Accountant accounts under their organisation
- Salesman goes On Duty / Off Duty from mobile
- While On Duty, salesman's GPS location is tracked every 5-10 seconds
- Owner sees live map with salesman markers (like Blinkit/Zomato delivery tracking)
- Route trail (polyline) drawn on map showing where salesman travelled
- If salesman stops for 5+ minutes, owner gets push notification + in-app alert
- Salesman submits orders from mobile (works offline, queues and syncs)
- Owner and Accountant see all orders in real time
- Owner can update order status (Pending → Confirmed → Delivered → Cancelled)
- When order status changes, salesman gets in-app notification
- When new order submitted, owner gets push notification
- PWA installable on Android and iOS (shows install prompt)
- Real-time sync via Firestore onSnapshot listeners + REST API fallback

7. AUTHENTICATION FLOW
================================================================================

1. User POSTs to /auth/login with email + password
2. Backend verifies password (bcrypt), checks isActive, checks lockout
3. Backend returns JWT token (30min expiry) + user object
4. Frontend stores token in localStorage (Zustand persist)
5. Frontend sets Authorization: Bearer <token> header on all requests
6. Frontend calls /auth/firebase-token to get a Firebase custom token
7. Frontend calls signInWithCustomToken(auth, customToken) to authenticate
   with Firestore SDK (needed for onSnapshot real-time listeners)
8. On page reload, main.jsx calls authStore.hydrate() which re-fetches
   the Firebase custom token and re-signs in

JWT payload: { uid, role, ownerId }
JWT expiry: 30 minutes (idle timeout)
Account lockout: 3 failed attempts → 15 min lockout
Password minimum: 12 characters
Password hashing: bcrypt with 12 salt rounds

8. REAL-TIME SYNC ARCHITECTURE
================================================================================

The app uses two layers of real-time sync:

LAYER 1 — Firestore onSnapshot (primary, instant):
- OwnerMap: listens to users collection (ownerId == owner.uid, filter On Duty in JS)
- OwnerMap: listens to stopEvents collection (ownerId == owner.uid, filter unresolved in JS)
- Owner notifications: listens to notifications collection (ownerId == owner.uid)
- Salesman notifications: listens to notifications collection (recipientId == salesman.uid)
NOTE: All Firestore queries use single where() clause to avoid composite index requirement.
Filtering is done in JavaScript memory after fetch.

LAYER 2 — REST API polling (fallback):
- OwnerMap falls back to polling /location/live every 5s if Firestore listener errors
- OwnerOrders uses REST API with 15s auto-refresh (Firestore listener removed due to auth issues)
- SalesmanOrders uses REST API on mount

LAYER 3 — Web Push (background, when app is closed):
- Backend sends push via web-push library when stop event detected or new order submitted
- Service worker (public/sw.js) receives push and shows OS notification
- Tapping notification opens app at /owner/map

9. GPS TRACKING FLOW
================================================================================

1. Salesman taps "Go On Duty"
2. App requests browser geolocation permission
3. On permission granted: POST /salesman/duty/start → creates dutySession doc
4. App calls navigator.geolocation.watchPosition()
5. On each position update: POST /location/ping { lat, lng, accuracy }
6. Backend stores locationPing doc AND updates users/{salesmanId}.liveLocation
7. Owner's Firestore listener on users collection fires instantly → map marker moves
8. Stop event cron (every 1 min): checks all active sessions for 5-min stops
9. If stop detected: creates stopEvent doc, sends push to owner, creates notification doc
10. Owner's Firestore listener on stopEvents fires → banner appears on map
11. Salesman taps "Go Off Duty": POST /salesman/duty/stop → session ended, dutyStatus = Off Duty
12. Owner's Firestore listener fires → marker removed from map

10. STOP EVENT DETECTION ALGORITHM
================================================================================

File: backend/src/jobs/stopEventDetector.js
Runs: Every minute via node-cron

Algorithm:
1. Fetch all dutySessions where status == "active"
2. For each session, fetch locationPings from last 10 minutes
3. Filter pings from last 5 minutes (STOP_DURATION_MS = 5 * 60 * 1000)
4. If fewer than 2 recent pings: skip
5. Take anchor = first recent ping
6. Check if ALL recent pings are within 50 metres of anchor (haversine distance)
7. If all within radius AND no open stopEvent for this session:
   - Reverse geocode location via OpenStreetMap Nominatim
   - Create stopEvent doc
   - Create notification doc for owner
   - Send Web Push to owner (with 3 retries, 30s apart)
8. If NOT all within radius AND there IS an open stopEvent:
   - Mark stopEvent as resolved
   - Create "moving again" notification for owner
   - Send Web Push to owner

11. ORDER OFFLINE QUEUE
================================================================================

File: frontend/src/pages/salesman/NewOrder.jsx

When salesman submits an order while offline:
1. Order is saved to localStorage key "order_queue" as JSON array
2. Toast shows "No connection — order saved and will submit when online"
3. Event listener on window "online" event triggers flushQueue()
4. flushQueue() iterates queue, POSTs each order to /orders
5. Successfully submitted orders removed from queue
6. Failed orders remain in queue for next retry
7. SalesmanOrders page shows queued count banner

14. KNOWN ISSUES & IMPORTANT NOTES
================================================================================

1. FIRESTORE COMPOSITE INDEXES:
   All Firestore queries intentionally use only ONE where() clause.
   Multi-field filtering is done in JavaScript memory.
   Reason: Composite indexes require manual creation in Firebase Console.
   If you add orderBy() to any query, it will fail with FAILED_PRECONDITION error.

2. RENDER FREE TIER SLEEP:
   Backend sleeps after 15 min of inactivity. First request takes ~30 seconds.
   Upgrade to Starter ($7/mo) for always-on.

3. SPA ROUTING ON RENDER:
   frontend/public/_redirects contains "/* /index.html 200"
   This file is copied to dist/ on build and tells Render to serve index.html
   for all routes. Do NOT add rewrite rules in Render dashboard — they conflict.

4. FIREBASE PRIVATE KEY ON RENDER:
   Paste the key with literal \n characters (not real newlines) in Render env vars.
   The backend code does .replace(/\\n/g, '\n') to convert them.

5. FIREBASE AUTH REQUIRED FOR FIRESTORE:
   The frontend uses Firebase custom tokens (minted by backend via Admin SDK)
   to authenticate with Firestore for onSnapshot listeners.
   If /auth/firebase-token fails, Firestore listeners will fail silently.
   Pages fall back to REST API polling in this case.

6. GPS ON iOS:
   iOS Safari requires HTTPS for geolocation. Works on the deployed site.
   Does not work on http://localhost on iOS.

7. PUSH NOTIFICATIONS ON iOS:
   Requires iOS 16.4+ and the app must be installed to home screen (PWA).
   Does not work in regular Safari browser tab on iOS.

8. OWNER'S ownerId FIELD:
   For Owner users, ownerId == their own uid.
   For Salesman/Accountant, ownerId == their owner's uid.
   This is used to scope all queries.

9. ADMIN USER:
   Created once via: node backend/scripts/createAdmin.js
   Credentials: admin@salestrack.com / Admin@123456
   Admin does NOT have an ownerId.
